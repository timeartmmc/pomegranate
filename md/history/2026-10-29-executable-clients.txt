POM EXECUTABLE CLIENTS: RECORDED IMPLEMENTATION EVIDENCE

Recorded 2026-10-29 for the unpublished executable-client milestone. These are
dated verification results, not guarantees for later checkouts or a publication
claim. EXECUTION.md and QUERIES.md own current usage and ARCHITECTURE.md owns
their boundaries. The subsequent execution/cache integration plan is complete;
consumer migration remains separate.


Gate 1: The strict execution prototype covers required and optional inputs,
JSON commands, native uploads, exact success envelopes, typed failure guards,
snapshots and cancellation. Positive and expected-error consumers additionally
cover browser uploads and heterogeneous success/page item types. ResponseError
aliases the existing QueryResponseError constructor, preserving its name,
construction and instanceof behavior.

Gate 2: executionClients selects complete surface bindings. Direct calls,
ordinary queries and both pagination profiles share execution-runtime.ts.
Only selected executable clients emit call-runtime.ts, which owns direct-call
construction and default AbortController creation. Query-only output retains
its earlier platform declaration requirements.
The operation's own parser is authoritative for error provenance; pagination
can add protocol issues only after that parse. Regression checks reject forged
request parsers, replaced results and reassigned execution scopes. Selection,
determinism, read-only drift and cleanup protections cover execution modules
and shared helpers. Execution-only output has no TanStack dependency.

Gate 3: The complete bun run verify passed independently on Node 22.18.0,
24.0.0 and 26.12.1 with pinned Bun 1.4.3: 647 tests passed on each runtime.
Each run includes formatting, build, strict types, type-aware Oxlint, real
Chromium Fetch and mounted query/infinite/mutation hooks, the standalone JSON
example, declaration publication/downstream consumers, and a packed install.
The isolated consumer uses TypeScript 5.7.3, Zod 4.6.6, Node 22 types and
Query Core 5.104.5; source checks use TypeScript 7.0.2 and Zod 4.6.7. Its 69-file
package inventory includes required notices and excludes tests/private inputs.
It executes generated TypeScript on Node and Bun and emitted JavaScript on Node
after removing the compiler, formatter and YAML parser. Native output compiles
without DOM libraries. Execution-only output compiles and runs before TanStack
is installed.

Board review found gaps in the initial full-suite evidence: query-only sources
required an unnecessary AbortController declaration, the example transport lost
the legal __proto__ response header, and parse-count cleanup failed when run
alone against fresh lazy Zod methods. All three are corrected and covered by
regressions. Query-only ordinary/cursor/offset sources now typecheck with types: []
and no DOM libraries, using only platform signal/callback/URL declarations.
The packed consumer repeats that check with minimum dependencies. Raw, recovery
and legacy parsed paths preserve prototype-related header names, and parse-count
verification runs independently and repeatedly without cleanup failures.

Response instrumentation runs against a supplied raw executor and the example
transport's shared raw and legacy parsed entries, including application-owned
recovery. Three successful responses and one denial produce four body reads,
four JSON parses and four schema passes. There is no parsed-success capture
adapter. Recovery, deadlines, locale, session fencing and mutation success
effects remain application-owned in the synthetic integrations.

Comparison: node scripts/benchmark-execution.ts uses handwritten bindings over
the identical shared core and runs both implementations through the same direct
acceptance checks. Eleven application endpoint bindings become zero; the sample
binding source changes from 2,079 to 71 bytes. Query key factories were already
generated before this milestone, so it claims no new key-factory deletions.
The shared executor still owns credentials, attempts, deadlines, locale,
sessions and file bodies; application code still owns cache effects.

On this machine, median TypeScript checks were 334.1 ms handwritten and 345.7 ms
generated. Median direct calls were 2.3 and 2.2 microseconds respectively.
Ordinary query functions measured 1.6 microseconds before the refactor and
1.3 afterward against baseline 6b0d7fbc79ee63ecdfa0a5218d5ae4a8068e8662.
These synthetic timings are diagnostic, not CI thresholds or application
performance promises; no material runtime regression appeared in these paths.

The representative two-surface output is 125,069 unminified TypeScript bytes,
including notices. Selecting executable clients adds 8,681 bytes when queries
are already selected; execution-only support adds 16,912 bytes over core output.
The query runtime extraction itself adds 4,226 source bytes when execution is
omitted. Bundled size and a future application's typecheck/network costs require
that application's own measurement.
